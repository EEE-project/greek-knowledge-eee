## 2026-09-05

- **The word-fusion bug from 2026-09-04 below was not actually fixed -- found by a `/code-review` pass against the already-pushed branch, fixed properly this time at the root, and re-verified with a broader check than the one that missed it the first time.** Two independent review angles, run against the real committed `words/*.md` content (not just unit tests), both found the same class of bug still shipping: Angle I measured 496 fused instances across 245 of 465 LSJ-bearing files; Angle B measured 439 across 230 (independently-written scripts, close but not identical -- treat as "~450-500 across ~230-245 files", not either number as exact).
  - **Real root cause in `okfbuild/sources/lsj_index.py`**: `_resolve_dialect_scope()`'s `flush_text()` collapsed accumulated text via `" ".join(text.split())`, which strips ALL leading/trailing whitespace rather than just collapsing internal runs -- so a real trailing space right before a citation boundary (e.g. "Ion. " ahead of its `<bibl>`) was silently deleted every time, not just in the one case the previous fix's check happened to look at. The same fix was also applied to `_resolve_dialect_scope()`'s `flush_pending_as_prose()` (a dialect marker with nothing to attach to, falling back to plain prose, was appended with no leading-separator check -- real example, μιν's own entry: "= νιν" directly followed by "Dor." with zero space) and, defensively, to `_extract_text()`'s own recursive concatenation (`"".join(parts)`), which has the identical structural flaw one level deeper even though no confirmed real headword in the current corpus currently triggers it -- investigating ἐρύκω's real fused entry ("ἐρυκέμεν εὐρύοπαΖῆν") originally suggested this was the mechanism, but tracing it to the raw XML found something different (see below).
  - **A real regression caught mid-fix, before it shipped**: a first attempt at the boundary-space rule checked only "previous doesn't end in whitespace AND new text doesn't start with whitespace" -- symmetric, and wrong, because it also inserted an unwanted space before ordinary attached punctuation. Diffing a regenerated file against `main`'s own already-committed, correct text caught it directly: real content "c. inf., it is good" (comma directly after the period, correct as shipped on `main`) came out as "c. inf. , it is good" once regenerated with the first attempt. Fixed with one shared, precisely-asymmetric helper, `_needs_boundary_space()`: a space is inserted only when the *next* piece starts with a genuine word character (checked via a Unicode-aware `\w` regex, not mere non-whitespace) -- attached punctuation starting the next piece never gets a leading space, and a previous piece ending in an opening bracket/paren (`(word` must stay `(word`, not `( word`) is the matching exception on that side. Used consistently everywhere text_parts/parts gets built up, plus 7 new tests exercising the rule directly (word-to-word fusion in both directions through `_extract_text()`, an abbreviation's period still wanting a following space before a real word, attached punctuation never gaining one on either side, the opening-bracket exception, already-whitespace boundaries, and the exact real "c. inf.," shape reproduced through `_extract_text()` itself).
  - **Re-verified with a broader check this time, not just the narrow one that missed it before**: scanned the entire regenerated corpus for any lowercase letter (Latin or Greek) directly touching an uppercase one -- a much wider net than "does a word touch the tag's own `**[`". Found 3 residual matches, all individually traced to real, raw XML and confirmed NOT to be the fusion bug: two are legitimate scholarly abbreviations with no space by convention (`FGrH`, a standard citation for *Fragmente der griechischer Historiker*; `aB*`, an epigraphic line/side notation) that happen to mix case; the third (ἐρύκω's `εὐρύοπα`/`Ζῆν`) is a genuine, isolated gap in Perseus's own raw Beta Code digitization -- a single, unsplit text node with no element boundary anywhere near it for any code-level fix to hook onto -- now documented as a fourth known Beta Code limitation in [`references/sources/lsj.md`](references/sources/lsj.md), the same way the three limitations discovered in 2026-09-03's entry below already are.
  - `data/lsj-cache/` rebuilt fresh again (465 entries this time); all `words/*.md` regenerated once more to carry the real fix. Full suite: 325 passed, 7 deselected (integration); `ruff check` clean.
- **Four smaller robustness findings from the same `/code-review` pass, none affecting real generated content today (all either confirmed dormant or pure parsing/caching robustness), fixed anyway**: `_YEAR_RANGE_RE` (`lsj_periods.py`) was missing `re.IGNORECASE`, unlike its 7 sibling date-regexes, silently dropping a lowercase/mixed-case year-range date like "384-322 b.c."; `_read_tlg_map_cache()`/`_read_frontmatter_cache()` (`lsj_periods.py`) only caught `json.JSONDecodeError` on a corrupt cache file, missing `UnicodeDecodeError` (a `ValueError` sibling, not a subclass, raised by `.read_text()` itself on invalid UTF-8 from e.g. a process killed mid-write) -- both now gracefully rebuild instead of crashing, matching what their own docstrings already promised; an empty/whitespace-only `<gram type="dialect">` (`lsj_index.py`) produced a non-empty, truthy `dialects=("",)` tuple that could render a malformed `**[]**` tag, now filtered the same way `_build_citation()` already guards `author_abbreviation`; `_decode_cached_entry()` (`lsj_index.py`) raised an uncaught `KeyError` on a same-`format_version` cache dict missing an expected field instead of the `_CACHE_MISS` its docstring promises -- the version stamp exists specifically to make this kind of drift safe, and now does for this shape too. 7 new tests, one per case plus the two symmetric cache-reader fixes; `data/lsj-cache/`/`words/*.md` not regenerated, since none of these four are reachable from any real content in the current corpus.

## 2026-09-03

- **LSJ is now genuinely functional end-to-end, closing the gap the earlier wiring-only pass left open** -- downloaded the real 27-file Perseus TEI-XML dump (~270MB) and made the "Ancient Greek meaning" section actually produce real content instead of always being empty.
  - Rearchitected `LSJIndex` to match `CachedWiktextractIndex`'s proven shape rather than repeat the exact problem that pattern was built to fix: a new `CachedLSJIndex` resolves and caches only the headwords a course actually looks up, as small per-headword JSON files under `data/lsj-cache/` (git-tracked, plain), instead of parsing all 27 files (~270MB) into memory on every process. The raw TEI-XML dump itself is a one-time, local-only, gitignored download to `data/lsj/` (matching `data/wiktextract/`'s pattern) -- `.gitattributes`' now-unneeded Git LFS tracking for it removed entirely.
  - **Discovered only once the real dump was parsed**: headwords and Greek body text in the real files are Beta Code (e.g. `key="no/stos"` for νόστος), not Unicode Greek -- the small hand-written test fixture predates this and uses real Greek characters directly, so nothing surfaced the gap until real data was actually downloaded. Converted via the `beta-code` PyPI package (perseids-tools, the same organization as Perseids Morpheus, already a dependency here). Conversion is element-aware, not whole-text: entries mix Beta Code Greek with plain English glosses and bibliographic abbreviations in the same entry, and naive whole-text conversion mangles the English (e.g. "good" -> "γοοδ") -- only text within a `lang="greek"`-tagged element (or its descendants) gets converted. Known, accepted limitation inherent to Beta Code itself, not fixed: a literal parenthesis used editorially inside a Greek span (e.g. a cross-reference like "(ne/omai)") is ambiguous with Beta Code's own breathing-mark notation and gets misconverted.
  - **Also discovered only against the real files**: their DOCTYPE declares 2 parameter entities -- `%TEI.XML "INCLUDE"` (genuinely internal) and `%PersDict PUBLIC ... "http://www.perseus.tufts.edu/DTD/1.0/PersDict.dtd"` (an *external* parameter entity, actually referenced via `%PersDict;`, confirmed directly against the real files) -- which `defusedxml`'s default policy (correctly) rejects, since it forbids all entity declarations unconditionally. Fixed with a custom `_LSJXMLParser` that narrows the check to general entities only (the ones a real attack payload would use, referenced from document content via `&name;`, never possible via a parameter entity's `%name;`, which is usable only within the DTD itself) -- verified to still correctly reject the existing billion-laughs security fixture, and confirmed empirically (no network activity during a real parse) that Python's non-validating expat parser never actually resolves `%PersDict;`'s external content regardless.
  - Raw extracted entry text also had its original XML indentation preserved verbatim as embedded whitespace runs; normalized to single spaces for clean prose when embedded in a rendered concept file.
  - Verified against the real dump directly (116,168 headwords) and end-to-end via the real pilot acceptance suite: `words/νόστος.md` and 464 other course-vocabulary word files now carry a genuine, correctly-formatted "Ancient Greek meaning" section citing real LSJ prose (e.g. νόστος: "νόστ-ος, ὁ ... return home, Hom. ... Il. 10.509", correctly citing Homer/Iliad). `data/lsj-cache/` populated with 636 real entries from that run. 1 of the 465 real files (`words/ὄϊς.md`) surfaced a third minor, known limitation: LSJ's own editorial bracket notation can incidentally produce a `[^...]`-shaped substring that collides with OKF markdown's footnote-reference syntax -- cosmetic, not a correctness issue (`okf.py`'s own footnote-definition logic only ever emits a definition for an id matching a real cited source, so this is an unresolved reference, never a duplicated/corrupted footnote); not fixed, see `references/sources/lsj.md` and a new comment in `okf.py` (the risk is general, not LSJ-specific) for why. 5 new tests against fixture data mirroring `CachedWiktextractIndex`'s own test shape (resolves from dump, persists across instances without the dump, caches confirmed absence, miss-without-dump is not cached, still rejects the billion-laughs payload); full suite (244 passed, 1 skipped) and ruff clean.

- **Fixed `okf.write()` duplicating a concept's citation footnote when rewriting an existing file for an unrelated frontmatter-only change** (e.g. `pipeline.py`'s pruning step flipping `status` to `deprecated`) -- e.g. `read()`-ing a file, changing one field, and `write()`-ing it back would leave the same `[^id]: ...` footnote definition on disk twice. Root cause: `ConceptFile.body` can already end with a footnote-definitions block from a previous `render()` call (`read()` reconstructs `body` as everything after the frontmatter fence, footnotes included, by design), but `render()` unconditionally appended a freshly-computed footnote block on top without checking whether one was already there. First surfaced live this session when an under-scoped pipeline example accidentally pruned two real files (`grammar/aorist-3pl-osan.md`, `culture/cavafy.md`), both reverted at the time; this fix addresses the underlying mechanism, not just that one trigger. Fixed by stripping any existing footnote-definition lines from `body` before recomputing referenced ids and re-appending -- also self-heals a file already corrupted by this bug, if rewritten again. Verified: a real reproduction (write with a citation, `read()`, flip `status`, `write()` again) now shows the footnote exactly once, both before and after fixing; full suite (235 passed, 1 skipped) and the real integration pilot run unaffected.

- **Gap-filler candidate resolution, pronoun, and budget-cache fixes** — found and fixed chasing the first real gated pilot runs (small real budgets against the OpenRouter-backed `GapFillerConfig`, `--run-paid-llm-tests`), each verified against real, paid API calls, not just unit tests.
